# How to monitor Japanese suppliers for company closures and address changes

If you maintain a list of Japanese suppliers in a CRM, ERP or procurement system, the useful question is: **which records should we review, and what did we actually check?** A company-name search alone does not answer that question for an existing portfolio.

This workflow uses the National Tax Agency's corporate-number daily difference files and an exact list of 13-digit corporate numbers. It is designed for supplier monitoring, KYB record maintenance and CRM company updates. It does not calculate Japanese supplier risk scores or replace a legal company-status check.

The sample was generated by a local release check on 2026-09-20 against **one NTA publication dated 2026-08-25**, file 27873, archive `diff_20260825.zip`. Its 2,222 source rows were inspected. It is not a customer watchlist or live monitoring result.

The first record is the historical NTA entry for 旭化成パックス株式会社. A closure event is not a reason to automatically terminate a supplier. Event history, successor records and the purpose of your relationship require review.

The second input is a **format-only test string**, not a source-verified company identifier. It illustrates why “no matching event” cannot establish that an input identifies a real company. The Actor validates the 13-digit input format; it does not verify issuance, the corporate-number check digit or present legal status. Use your own verified identifiers for a real review.

## Run the same workflow on your own supplier list

1. Export the verified corporate-number column from the system that already holds your supplier list. Import identifiers as **Text** to avoid spreadsheet conversion or scientific notation. Omit the heading and company names; do not reuse the format-only test string as a supplier.
2. Open [Japan Supplier & KYB Change Monitor](https://apify.com/japan_signal_lab/japan-signal-lab). You can inspect its historical one-company demo first. The demo has an expected PPE price of **$0.0152**, not $0.
3. Replace the demo number, clear the historical end date and choose a 30-day initial check. API users can continue using the existing `companyNumbers` array; do not accidentally keep demo numbers in both fields.
4. Inspect the **Dataset** for matching changes. Each event keeps its official process code, history sequence, effective date and source identity.
5. Export the **Company-by-company check report (CSV)** and retain its companion JSON. The CSV tells you which numbers produced events and which could not be fully checked. The JSON gives file coverage and dates with no available publication.

## Use the result in your CRM or supplier-review process

Join the report back to your existing list by **exact corporate number**, not a fuzzy company-name match. Route emitted events using the existing `workflowHint`: name/address changes can go to master-data review; status or merger events can go to a counterparty reviewer. Keep the source fields separate from your internal decision.

Do not turn a missing report row into “no change.” `UNCONFIRMED` means the source or processing limit prevented a complete check. `NOT_MONITORED` means the monitoring cost limit excluded that input number. `NO_MATCHES_IN_SELECTED_FILES` refers only to files actually selected and inspected. Weekend or missing-publication dates are not silently treated as checked days.

A run may return an event and still be `PARTIAL`: a remaining balance smaller than one additional event can cause the existing SDK cost guard to stop processing. The returned event remains evidence; completeness is a separate question. The report does not raise your spending limit.

## Repeat only when the workflow is useful

After reviewing the first result, choose one day for a regular check or seven days for catch-up. An unchanged supplier list can legitimately produce no new events. Compare official identities and source dates before treating repeated exports as new work.
